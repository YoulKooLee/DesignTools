## 一、文案配置

### 1.1 「大屏预览」从哪来 —— 现状是不读任何数据的

**必须说清楚：设计稿里那块预览是装饰，不是真数据。**它只有 4 个固定格子、每个格子里 5 根写死高度的柱子（38%/72%/52%/64%/44%），标题和菜单会跟着输入变，但图表区是死的。写它时只为了占出「顶栏 + 4 宫格」的形状。

真实编辑器里**已经有**一张真缩略图：`updateLayoutPreview()`（第 3000 行附近，布局配置弹窗里那张）。

它做了什么：

```
solveLayout(layoutConfig.W, layoutConfig.type, layoutConfig.tier)
  → 按列数 n、行数 m 画出左带图表格 / 中间三维区 / 右带图表格
  → 尺寸全部按 k = 预览宽 / layoutConfig.W 等比缩放
```

它读的正是**布局配置**：宽度 `W`、布局类型 `type`、密度 `tier`。但有一个缺口：

```js
function updateLayoutPreview() {
    const s = solveLayout(layoutConfig.W, ...);   // ← 只认自动布局
    ...
}
```

**自由布局模式（`freeLayout.items`）没有分支**，所以现在自由布局下这张缩略图是「按自动布局画的」，不是真的。

三个可选做法（差别就是"真到什么程度"）：

| 方案 | 画什么 | 代码量 | 缺点 |
|---|---|---|---|
| **P1 文案预览条** | 顶栏（标题+菜单）+ 4 个灰块示意，不读布局 | ~20 行 | 看不出布局，跟你现在的设计稿一样 |
| **P2 比例示意** | 顶栏 + 三维区位置/大小 + 左右各几列（按 `solveLayout` 的 n/m/带宽），**不画每张卡** | ~35 行 | 卡片不逐张画，只能看出"几列、多宽" |
| **P3 真缩略双通道** | 自动模式走 `solveLayout`；自由模式按 `freeLayout.items` 的 x/y/w/h × k 逐张画 | ~60 行 | 预览只有 520px 宽时，12 个格子每块约 40×30px，看不出内容只能看分布 |

我倾向 **P2**：文案页的目的是「确认标题和菜单在屏上的样子」，不是「审布局」；P3 在这个尺寸下退化成一片小方块，反而更难读。但你要的真「从布局配置读取」是 P3。

**无论选哪个，都必须做的一件事**：预览区标「缩略示意 · 不代表实际图表内容」，并做成只读（不绑任何点击）。否则用户会以为能点。

### 1.2 菜单个数 3–8

**改动点只有两处：**

| 位置 | 现在 | 改成 |
|---|---|---|
| `initTextConfig()` 第 4170 行 | `for (let n = 2; n <= 6; n++)` | `for (let n = 3; n <= 8; n++)` |
| 第 4157–4164 行加载存档 | 只判 `Array.isArray(p.menus) && p.menus.length` | 加载后把长度夹到 3–8：`< 3` 补默认名，`> 8` 截断 |

**连带必须处理的老数据**：现有存档里如果存过 2 个菜单（`['总览','分析']`），下限提到 3 后会显示「2 个菜单」但按钮里没有 2，出现"没有任何按钮高亮"的错位状态。所以载入时必须补齐到 3。

**实测结论（1440×900 窗口，真编辑器，非估算）：**

| 场景 | 总宽 | 换行 | 文字溢出 | 距左侧标题 | 距右侧按钮 |
|---|---|---|---|---|---|
| 3 个（现状基线） | 136px | 否 | 无 | 483px | 509px |
| 5 个 | 214px | 否 | 无 | 444px | 470px |
| 6 个字×6 个 | 359px | 否 | 无 | 371px | 398px |
| 8 个（4 字） | 344px | 否 | 无 | 379px | 405px |
| **8 个（6 字长名）** | **472px** | **否** | **无** | **315px** | **341px** |

最坏情况（8 个 6 字名）仍有 315px / 341px 余量，**不需要额外的紧凑样式**。现有 `padding: n <= 3 ? 34 : n === 4 ? 26 : 16` 已经够用。

> 为什么这么宽松：顶部菜单是 `position:absolute; left:50%; translateX(-50%)` 居中，而 stage 是 3200 逻辑宽按窗口等比缩放，8 个页签在缩放后只占 472px。若将来出现 12 个字以上的菜单名，才需要改成 `padding: 10px`。

**设计稿同步**：菜单个数按钮从 `2/3/4/5` 改为 `3/4/5/6/7/8` 六个；`#menu-names` 现在的 `grid-3` 固定 3 列，8 个菜单会变 3 行且最后一个落单 → 改为按个数取列数：`≤6 → 3 列`、`7–8 → 4 列`。

## 二、指标管理：两个属性

### 2.1 所属数据表 —— 字段已经有了，只是没露出来

**这不是新增属性。**自定义指标保存时已经写了（`saveCalcIndicator()`，第 4862 行起）：

```js
const d = {
    id, name, mod, unit, ...,
    src: t.name,          // ← 事实表名称，已在
    custom: true,
    datasetId: C.datasetId  // ← 事实表 id，已在
};
```

内置的 4 条示例指标没有 `datasetId`（`custom` 为假），它们的 `src` 是示例文案。

**所以要做的只是 UI 显性化：**

1. 指标管理行内加「表」小标签：`门诊明细` / `内置示例`
2. 顶部筛选加「数据表」下拉（选项来自 `DATASETS` + 「内置示例」）
3. 自定义指标被删表时显示 `表已删除`（红字），和现有 `datasetById()` 的兜底一致

成本：纯前端展示，不动数据结构。

### 2.2 所属菜单 —— 真新增，且会动数据模型

**现状有一个必须知道的事实：**

```js
function switchTab(el) {
    document.querySelectorAll('.nav-tab').forEach(t => t.classList.remove('active'));
    el.classList.add('active');   // ← 就这三行
}
```

**切换菜单只换高亮，图表内容一个字都不变。**所以「不同菜单切换不同图表」现在完全不存在，是从 0 建的功能，不是加个字段。

**三种建模方式：**

| | 做法 | 一个指标能出现在几个菜单 | 每个菜单能不同形式 | 代价 |
|---|---|---|---|---|
| **M1 指标绑菜单** | `ind.menuId` 单值 | 只能 1 个（要多菜单就建重复指标） | — | 最直白，但指标会重复增殖 |
| **M2 上屏关系绑菜单**（推荐） | `selItems[].menuId`，指标本身全局 | 多个 | 能 | `selItems` 结构改 + 容量判定改 + 渲染改 |
| **M3 指标带菜单数组** | `ind.menus = ['m1','m2']` | 多个 | 不能 | 结构简单，但同一指标在两菜单必须同形式 |

选 M2 的理由：**「指标是什么口径」和「在哪个菜单用什么形式展示」本来就是两件事**。门诊人次在「总览」用卡片、在「门诊专题」用柱状图，是很自然的需求；M1 要建两条一模一样的指标，M3 做不到不同形式。

**M2 下必须一起定的三件事**（不定就做不下去）：

**① 容量按菜单独立，还是整屏共享？**

现在是 `chartCap()` = 12、`kpiCap()` = 3，整屏一套。8 个菜单共享 12 个图表位 = 每菜单 1.5 张，不可用。

→ **建议按菜单独立**：每个菜单各自 12 图表位 + 3 KPI 位，切换菜单时底部计数变成「本菜单图表 4/12」。超限提示也改成「本菜单图表位已满 12/12」。

**② 布局是共用一套壳，还是每个菜单一套？**

`freeLayout` 现在是整屏一份。如果每个菜单都要独立布局：存档从 1 份变 8 份、编辑器要带"当前在编辑哪个菜单"的上下文、`nanshan_freelayout` 结构要迁移——工作量翻倍，而且用户很容易把某个菜单的布局搞乱找不回来。

→ **建议共用一套壳**：12 个卡位 + 3 个 KPI 位的位置固定，每个菜单往里填不同的图表。切菜单不塌、不重排，视觉也是最稳的（各菜单版式一致，只换内容）。

**③ 菜单必须有稳定 id**

现在 `textConfig.menus = ['总览','分析','监控']` 是纯字符串，没有 id。如果归属按**索引**存（`menu: 0`），用户把「分析」拖到第一位、或删掉「总览」，所有指标的菜单归属会整体错位。

→ **必须迁移**：`menus: [{id:'m1', name:'总览'}, …]`。老存档按序号生成 id（`m1…mN`），一次性迁移，之后菜单增删不丢归属。这是隐蔽但致命的一点。

**M2 的 UI 落法**（不然列表没法用）：指标管理页加一行菜单页签（`总览 | 门诊 | 应急处置 | …`），列表里的「上屏开关 / 位次」都是**当前选中菜单下的**；另加一列「所属菜单」，用标签显示该指标出现在哪几个菜单（`未上屏` 时显示灰字）。

## 四、风险与边界

1. **8 菜单 × 12 图表位 = 96 个上屏项**。指标管理如果不带"当前菜单"上下文，用户会分不清哪个开关管哪个菜单。所以 M2 的菜单页签是必需的，不是可选的装饰。
2. **老存档迁移不可回退**：`ds_sel`、`ds_text_config` 结构变了，迁移后旧版编辑器打不开。迁移前先备份 localStorage 快照（在代码里写一份 `ds_sel_bak_v1`）。
3. **共用一套壳的代价**：如果某菜单只要 2 张图，其余 10 个卡位会空着（或显示空占位）。需要定"空卡位是否显示"——建议空位不渲染，露出背景。
4. **切换菜单时 KPI 组对齐**：自由布局里 KPI 卡片有组内对齐逻辑，切菜单换内容后如果 KPI 数量变化，需要重新跑一次 `alignKpiGroup`，否则会重叠。
5. 菜单数量从 8 减到 3 时，被删菜单上的指标归属怎么处理——建议**保留归属但标记"菜单已删除"**，恢复菜单时自动回来（和示例指标"隐藏可恢复"同一思路）。
