## 二、三个必须先说的发现

### 发现 1：容量本来就不是写死的

```js
function chartCap() { return (window.__chartSlots || []).length; }   // 3102 行
function kpiCap()   { return Math.max(2, Math.min(kpiFitCount(), layoutConfig.kpiCount)); }
```

`__chartSlots` 是 `solveLayout()` 算完后真实生成的卡位数组（3308 / 3349 行）。默认 3200 宽 + A 型 + 3 行密度 = `2 × n × m = 12`，所以「12」只是默认参数的产物，不是常量。

**结论：你说的「图表位由布局配置生成」已经成立。**不需要新建容量系统，只要让 `layoutConfig` 按菜单存，容量判定自动跟着菜单走。这是好消息，阶段 2 的工作量比预想小。

### 发现 2：`layoutConfig` 里有一份死掉的 title / menus

```js
let layoutConfig = {
    W: 3200, type: 'A', tier: 3, kpiCount: 3,
    title: '数据可视化大屏设计器',        // ← 全代码 0 处读取
    menus: ['总览', '分析', '监控'],      // ← 全代码 0 处读取
};
```

真正的菜单源是另一份 `textConfig`（存 `ds_text_config`），渲染用 `applyTextToPage()`。这两份重复且会跑偏——**必须清掉 `layoutConfig` 里的**，否则将来改菜单可能出现"改了一份、渲染另一份"。

### 发现 3：三个存档要一起改

| 键 | 现在 | 变成 |
|---|---|---|
| `ds_text_config` | `{title, menus:['总览','分析','监控']}` | `{v:2, title, menus:[{id:'m1',name:'总览'},…]}` |
| `ds_layout` | 单对象 `{W,type,tier,kpiCount,layoutMode}` | `{v:2, active:'m1', byMenu:{m1:{…}, m2:{…}}}` |
| `ds_freelayout` | 单对象 `{W,H,items:[…]}` | `{v:2, byMenu:{m1:{…}, m2:{…}}}` |
| `ds_sel` | `[{ind,type,dims,agg}]` | `{v:2, byMenu:{m1:[…], m2:[…]}}`（阶段 3） |

**必须一次迁完**：分两次迁移，第二次要处理"已经迁了一次"的混合态，出错概率高得多。

## 四、风险

1. **切菜单要重渲染整屏 ECharts**（12 张图）。粗估 600ms 左右，会有可感知的顿挫。缓解：切换时先保底显示骨架、图表异步 init；实测后定是否需要缓存。
2. **8 个菜单 = 8 份布局存档**。一份自由布局约 2KB，8 份 16KB，localStorage 无压力。
3. **删菜单后存档保留但不回收 id**：删掉「分析」再加一个「分析」，会拿到新 id `m4`，旧布局不会自动回来。这是有意的（避免"删了又建"把旧数据意外复活），但要在界面上说明。
4. **`clearAllData()` 前缀扫 `ds_`** 仍然覆盖所有新键，不用改。
5. **中间态**：阶段 2 做完时是"每个菜单各有版式，但显示同一批图表"；阶段 3 才让内容真正分开。这个中间态可用但不好看，所以要连着做，不要停在阶段 2。
6. **迁移不可逆**：迁移前写 `_v1_bak` 三个备份键，出问题可回滚。

### 实测才发现的 3 个坑

1. **「没有自由布局」≠「新菜单」**：第一版用 `!freeByMenu[id]` 判断是否新菜单，导致 m1（本来用自动布局）切过去时继承了 m2 的自由布局。判据必须改成 `!layoutByMenu[id]`。
2. **预置菜单第一次切过去会是空白**：初始化只给首屏 `seedNeutralDemo`，`activateMenu` 里原本只 `selItems=[]`。改成「清单从没存过就继承上一个菜单，真没有才 seed」。
3. **迁移只在内存**：不立刻回写 v2 的话，每次打开都重新迁移一遍，而且无法判断哪些菜单真的被配置过。加 `upgradeStoresToV2()`。

### 已知边界

- 没切换过的菜单不建存档，第一次切过去时才继承当前菜单的版式与内容（不是凭空多出 8 条空记录）。
- 删菜单后其存档保留、id 不回收；再加同名菜单会拿到新 id，旧布局不会自动回来。
- 各菜单图表位数量由各自布局算出，不再是固定 12。

### 阶段 3 实测才发现的 4 个坑

1. **`loadSelection()` 每次从 localStorage 整体重置 `selByMenu`**：`activateMenu` 刚在内存里 clone 出目标菜单的清单，下一秒被还没落盘的旧存档覆盖 → 误判"没有任何清单" → 退化成示例兜底，表现为「切到没配过的菜单，内容变成默认 4 张」。改成只在内存为空时载入一次。
2. **`selIndexOf` 用 `===` 比数字和字符串**：DOM `dataset.ind` 取出来是字符串，`selItems[i].ind` 是数字，导致 `posTagHtml` 查不到 → 所有位次显示「未上屏」。统一按 `String()` 比较。
3. **载入时「先图表后 KPI」重排**：原 `selItems = charts.concat(kpis)` 会打乱顺序，同一张图切个菜单就从「图表 01」变「图表 03」。改成按原顺序保序裁剪。
4. **缩略图只按宽度缩放会撑出卡片**：pv-stage 高度超出 pv-box，标题条跑到卡片标题上重叠。改成宽高双约束 `min(availW/W, availH/H)` + `overflow:hidden`。
